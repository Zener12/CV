# Тема 0.1. Тензоры и autograd

Фундамент. Всё остальное в PyTorch — надстройки над тем, что здесь.

## Задача, которую мы решаем

У сети есть параметры — числа. Обозначим их все одним вектором **w**. Есть функция
потерь **L(w)** — одно число, показывающее, насколько плохо сеть справляется.
Обучение = поиск такого **w**, при котором **L** мала.

Градиент ∂L/∂w — вектор той же длины, что и **w**, где каждая компонента отвечает
на вопрос: *«если чуть-чуть увеличить этот параметр, насколько изменится ошибка?»*.
Градиент указывает направление наибольшего **роста** ошибки, поэтому шагаем **против** него:

```
w  ←  w − lr · ∂L/∂w
```

Вся сложность не в этой строке, а в том, как посчитать ∂L/∂w, когда L получается
из w через сотни операций подряд.

## Считаем градиент руками

Микро-модель: один параметр `w`, один вход `x`, одна цель `y`.
Предсказание `w·x`, ошибка — квадрат отклонения. Пусть `x = 2`, `y = 10`, `w = 1`.

Прямой проход, разложенный на элементарные шаги:

```
a = w · x       = 1 · 2   = 2
b = a − y       = 2 − 10  = −8
L = b²          = (−8)²   = 64
```

Обратный — идём **с конца**, на каждом шаге спрашивая «как выход этого шага зависит
от его входа?»:

```
∂L/∂b = 2b  = 2·(−8) = −16      (производная квадрата)
∂b/∂a = 1                        (вычли константу — наклон не изменился)
∂a/∂w = x  = 2                   (умножили на x)
```

Каждая производная **локальная**: она про одну операцию, её можно посчитать,
ничего не зная про остальные. Связывает их **цепное правило**: производная
композиции = произведение производных звеньев.

```
∂L/∂w = ∂L/∂b · ∂b/∂a · ∂a/∂w = (−16) · 1 · 2 = −32
```

Шаг с `lr = 0.1`: `w ← 1 − 0.1·(−32) = 4.2`.
Проверка: `a = 8.4`, `b = −1.6`, `L = 2.56`. Было 64.

Это ровно то, что делает `loss.backward()` — только для миллионов параметров
и сотен звеньев. Механика та же.

## Почему обратный проход, а не прямой

Если идти вперёд, за один проход получаешь производную **всего выхода по одному входу**.
Для 11.7 млн параметров нужно 11.7 млн проходов.

Если идти назад, за один проход получаешь производные **одного выхода по всем входам
сразу**. Один обратный проход стоит примерно как два прямых.

Причина асимметрии в форме задачи: **много входов и ровно один выход** (скалярный лосс).
Обратный режим выгоден именно в такой конфигурации. Если бы было наоборот — один вход
и много выходов — выгоднее был бы прямой.

Это **reverse-mode automatic differentiation**. Backpropagation — его частный случай
для нейросетей. Без этого приёма глубокого обучения бы не существовало.

## Как PyTorch строит цепочку

У каждого тензора есть флаг `requires_grad`. Если он `True`, PyTorch **следит**
за этим тензором.

Когда ты выполняешь операцию над отслеживаемым тензором, PyTorch не только считает
результат, но и **запоминает, откуда результат взялся**. У полученного тензора
появляется атрибут `grad_fn` — ссылка на объект, который знает: какая это была операция
(то есть формулу локальной производной) и какие тензоры были её входами.

Получается граф — **граф вычислений**. Три его свойства:

**Он строится во время прямого прохода, а не заранее.** Каждая операция достраивает узел.
Поэтому в модели можно писать `if`, циклы, менять структуру от батча к батчу.
Это называется define-by-run — главное отличие PyTorch от старого TensorFlow.

**Листья графа** — тензоры, которые ты создал сам, а не получил как результат операции.
Параметры модели — листья. У них нет `grad_fn`. Именно и только листьям `backward()`
кладёт результат в `.grad`. У промежуточных тензоров `.grad` останется `None`.

**Граф хранит промежуточные значения.** Чтобы посчитать `∂L/∂b = 2b`, нужно знать `b`.
Поэтому во время forward все промежуточные результаты остаются в памяти до backward.
Отсюда: **основной расход памяти при обучении — не веса, а сохранённые активации**,
и растут они линейно по размеру батча. Вот почему batch size упирается в память,
а инференс той же сети требует её в разы меньше.

### `grad_fn` хранит только последнюю операцию

В `a = w * x + c` операций две, а `grad_fn` покажет `AddBackward0`. Остальная цепочка
доступна через `next_functions` у самого `grad_fn` — по этим ссылкам `backward()`
и идёт назад.

## Что делает `backward()`

Вызывается на **скаляре**: `loss.backward()`. Дальше:

1. Идёт по графу от лосса назад.
2. На каждом узле умножает пришедший сверху градиент на локальную производную операции.
3. Дойдя до листа — **прибавляет** результат к его `.grad`.
4. Освобождает граф.

**`backward()` не меняет веса.** Совсем. Он только считает градиенты и кладёт их
в `.grad`. Веса меняет `optimizer.step()` — отдельный вызов, отдельный объект.
Возвращает `backward()` — `None`.

Разделение специально: между ними можно вклиниться — обрезать градиенты
(`clip_grad_norm_`), залогировать их норму, накопить ещё.

**Почему обязательно скаляр.** Производная одного числа по вектору — вектор.
Производная вектора по вектору — матрица (якобиан), и «шагать против якобиана»
бессмысленно. Поэтому лосс всегда сворачивают в одно число: по батчу берут среднее
(`reduction='mean'` по умолчанию). Иначе — `grad can be implicitly created only
for scalar outputs`.

**Граф освобождается.** Промежуточные значения выбрасываются сразу после использования.
Второй вызов `backward()` на том же лоссе упадёт:

```
RuntimeError: Trying to backward through the graph a second time
(or directly access saved tensors after they have already been freed).
```

Обойти можно флагом `retain_graph=True`, но в 99% случаев эта ошибка означает,
что ты не пересчитал forward.

Два типичных источника этой ошибки в реальном коде:
- забыт новый forward в цикле;
- лосс копится тензором (`total += loss` вместо `total += loss.item()`) — тогда `total`
  тянет живые графы всех итераций.

## Два независимых механизма — не путать

| Механизм | Что делает | Когда |
|---|---|---|
| «`.grad` только листьям» | градиент нелистового тензора посчитан, использован как транзит и выброшен | во время backward |
| освобождение графа | удаляются сохранённые промежуточные **значения** | после backward |

Второй отвечает за ошибку при повторном `backward()`. К пустому `.grad`
у промежуточного тензора он отношения не имеет.

**Освобождение графа не трогает `.grad` вообще.** Наоборот: `.grad` переживает
и backward, и step, и следующую итерацию — он живёт, пока его явно не обнулить.

| | Что это | Живёт до |
|---|---|---|
| `.grad` | результат, градиент параметра | явного `zero_grad()` |
| сохранённые значения графа | сырьё для вычисления градиента | конца `backward()` |

### `retain_grad`

Отменяет правило «только листьям» для конкретного тензора — поштучно, по умолчанию
выключено ради памяти. В отладке включают, чтобы посмотреть, не затухает ли градиент
по глубине сети.

### Правило про листья

**Лист — это про происхождение тензора, а не про его роль в обучении.**

- Все тензоры с `requires_grad=False` — листья, всегда, по определению.
  За ними autograd не следит, `grad_fn` у них не появляется никогда.
- Среди тензоров с `requires_grad=True` лист — тот, который создал ты,
  а не породила операция.

Практический вывод: **`.grad` заполнится, только если тензор одновременно лист
и требует градиента.** Отдельно ни один флаг ничего не гарантирует.
(Третье практическое условие: параметр должен реально участвовать в прямом проходе.
Слой создан, но забыт в `forward` — `.grad` останется `None`.)

## `zero_grad` — почему градиенты накапливаются

`backward()` делает `.grad += новый градиент`. Не `=`, а `+=`.

Если забыть. Пусть на каждом батче честный градиент равен 8, шаг `lr = 0.1`:

| Шаг | Накоплено в `.grad` | Реальный шаг |
|---|---|---|
| 1 | 8 | 0.8 |
| 2 | 16 | 1.6 |
| 3 | 24 | 2.4 |
| 100 | ≈ 800 | 80 |

Эффективный learning rate растёт линейно с номером шага. Через сотню-другую итераций
лосс уходит в `NaN`. Сеть не падает — она «обучается», просто расходится.
Молчаливый баг.

Почему PyTorch так сделан — три настоящие причины:

**1. Один параметр может участвовать в вычислении несколько раз.** В рекуррентной сети
одна матрица применяется на каждом шаге последовательности. Полная производная —
сумма вкладов со всех шагов. Накопление здесь математически правильное поведение.

**2. Несколько лоссов.** `L1.backward()` и `L2.backward()` дадут в `.grad` градиент суммы.
Это то же самое, что `(L1 + L2).backward()`, потому что производная суммы =
сумма производных. Практическая деталь: если `L1` и `L2` посчитаны из одного forward,
они делят общий граф, и первый `backward()` его уничтожит — нужен `retain_graph=True`
или, что проще, сложить лоссы и сделать один `backward()`.

Реальные случаи: многозадачная сеть (общий бэкбон, две головы), GAN,
вспомогательные лоссы на промежуточных слоях.

**3. Gradient accumulation.** Хочешь эффективный батч 64, а в память влезает 8.
Делаешь восемь прямых-обратных проходов по 8 примеров подряд, градиенты сами
суммируются, и только потом один `optimizer.step()`.

```
zero_grad()
повторить 8 раз:  forward на 8 примерах  ->  backward   (шага НЕТ)
step()
```

Две обязательные детали:

- **Лосс делить на число шагов накопления.** Стандартный лосс — среднее по батчу;
  просуммировав 8 средних, получишь величину примерно в 8 раз больше, чем среднее
  по 64, и эффективный LR подскочит в 8 раз.
- **Это не полный эквивалент батча 64.** BatchNorm считает статистики по тому, что
  физически лежит в батче — по 8 примерам. Градиенты как у 64, нормализация как у 8.

Поэтому PyTorch и не чистит `.grad` сам: он не может знать, закончил ты накапливать
или нет.

С PyTorch 2.0 по умолчанию `set_to_none=True` — вместо записи нулей `.grad` ставится
в `None`. Чуть быстрее и экономнее. Побочный эффект: до первого `backward()`
у параметра `.grad` будет `None`, а не тензор нулей.

## `no_grad` и `detach`

Граф нужен только для обучения. На валидации и инференсе он — чистые накладные расходы.

**`torch.no_grad()`** — контекстный менеджер: внутри него граф не строится вообще.
Есть и форма декоратора `@torch.no_grad()`.

Что важно: `no_grad` **не меняет арифметику ни на бит**. Значения совпадают.
Отличается только то, что у результата нет `grad_fn` и `requires_grad=False`.
Следствие: всё, что посчитано **из** такого тензора, тоже вне графа — отрезав ветку
один раз, назад её не пришьёшь.

`no_grad` — свойство **контекста выполнения**, а не тензора. Внутри блока
`w.requires_grad` остаётся `True`.

Типичный баг: по невнимательности обернуть обучающий forward — тогда
`backward()` падает с `element 0 of tensors does not require grad and does not
have a grad_fn`.

### Три способа «выключить градиент» — не взаимозаменяемы

| | Что выключает | На что влияет |
|---|---|---|
| `requires_grad=False` | отслеживание конкретного тензора | он не обучается, оптимизатор его не трогает |
| `torch.no_grad()` | построение графа в блоке кода | память и скорость |
| `model.eval()` | режим слоёв | BatchNorm использует `running_*` вместо статистик батча и перестаёт их обновлять; Dropout выключается |

Путают обычно `no_grad()` и `eval()`. Оси разные, ни один не подменяет другой.
На валидации нужны **оба**: `eval()` — чтобы метрика была правильной,
`no_grad()` — чтобы не жечь память.

**`.detach()`** — возвращает **новый объект-тензор**, но данные он **разделяет**
с исходным: одна память, без копирования. Изменение одного in-place отразится
на другом. Нужна независимая копия — `.clone().detach()`.

Для скаляра проще `.item()` — обычный питоновский `float`, никаких связей
ни с графом, ни с памятью.

## Обновление параметров: три варианта

Параметры — листья с `requires_grad=True`. Обновить их «в лоб» не выходит:

- **(а) `w = w - lr * w.grad`** — ошибки нет, но справа стоит **операция**,
  её результат — новый **нелистовой** тензор. Имя `w` теперь указывает на него,
  и на следующей итерации `w.grad` окажется `None` (листьям только).
  Плюс второй, более опасный баг: **оптимизатор запомнил ссылку на старый объект**
  и продолжает обновлять его — обучение идёт мимо модели, молча.
- **(б) `w -= lr * w.grad`** — `RuntimeError`: листовой тензор, требующий градиента,
  используется в операции на месте. Autograd отслеживает версии тензоров; значение
  листа может понадобиться при обратном проходе, и тихая перезапись дала бы
  неверный результат.
- **(в) то же внутри `torch.no_grad()`** — работает. Запрет снят: операция вне графа
  ничего испортить не может.

Именно так `optimizer.step()` и обновляет веса — изменение на месте внутри `no_grad`.
Никакой магии.

Общее правило, всплывающее постоянно: **присваивание имени не меняет объект,
на который имя указывало.** И: **оптимизатор держит ссылки на конкретные
объекты-параметры**, он не знает слова «модель».

## Learning rate и граница устойчивости

Для нашей модели (`pred = w·x + c`, квадратичный лосс) остаток после шага
умножается на постоянный множитель:

```
b_new = b · q,    где   q = 1 − 2·lr·(x² + 1)
```

При `x = 2` (то есть `x² + 1 = 5`):

| lr | q | Поведение остатка |
|---|---|---|
| 0.05 | 0.5 | уменьшается вдвое за шаг — сходится плавно |
| 0.1 | 0 | попадает в минимум за один шаг |
| 0.15 | −0.5 | перелетает, но сходится с колебаниями |
| 0.2 | −1 | колеблется вечно, не сходится **никогда** |
| 0.3 | −2 | удваивается каждый шаг — **расходится**, дальше NaN |

Общий результат: **для квадратичной функции градиентный спуск сходится тогда
и только тогда, когда `0 < lr < 2/λ`**, где `λ` — кривизна (максимальное собственное
число матрицы вторых производных). Здесь `λ = 2(x²+1) = 10`, отсюда граница `0.2`
и оптимум `1/λ = 0.1`.

**Граница расходимости вдвое больше оптимального LR.** Между оптимумом и границей —
зона, где шаг перелетает минимум, но всё равно приближается к нему.

### Связь с нормализацией входа

В формуле `q` стоит `x² + 1` — кривизна. **Чем крупнее по модулю входные данные,
тем круче парабола и тем меньше допустимый LR.** Если `x` был бы 20, то `x² + 1 = 401`,
и максимальный рабочий `lr` упал бы примерно до `0.0025` — в 80 раз.

Вот зачем нормализуют вход (`Normalize(IMAGENET_MEAN, IMAGENET_STD)`). Нормализация
приводит масштаб данных к единице и делает кривизну предсказуемой, а привычные
значения LR (1e-3, 1e-4) — рабочими. Подашь картинку в диапазоне 0..255 вместо 0..1 —
кривизна вырастет на четыре порядка, и `lr=1e-3` окажется далеко за границей
расходимости.

### Как это выглядит в реальном обучении

**Расходимость:** лосс растёт, потом `inf`, потом `NaN`. `NaN` заразен — попав
в один вес, за пару шагов расползается по всей сети. Первое, что проверяют
при `NaN` в лоссе, — не велик ли LR.

**Граница устойчивости — самый коварный случай.** Ничего не ломается, ошибок нет,
лосс просто стоит на месте на высоком значении. При этом параметры **меняются,
и сильно**: шаг перелетает минимум и оказывается ровно по другую сторону,
следующий возвращает обратно. Колебания с постоянной амплитудой, лосс из-за
симметрии стоит.

Это регулярно диагностируют как «модель слабая» или «данных мало» и лезут менять
архитектуру. **Лосс, застрявший на плато с первой эпохи, — в первую очередь
подозрение на слишком большой LR.** Вторая гипотеза — параметры вообще не двигаются
(всё заморожено, `lr=0`, градиенты не доходят); отличается одним взглядом на веса.

### Терминология

- Сходится или расходится **метод**, а не learning rate.
- Скорость такого убывания называют **линейной сходимостью**, хотя ошибка падает
  геометрической прогрессией. Термин исторический.
- Последовательность значений лосса — **последовательность**, а не **ряд**
  (ряд — это сумма).
- «Заморожены» бывают параметры (`requires_grad=False`). Градиенты — **обнуляют**.

## Про точность

`float32` даёт около 7 значащих цифр — отсюда `9.000001907` вместо ровных девяток
в режиме колебаний. При AMP часть вычислений идёт в `float16`, где значащих цифр
примерно 3, и такой дрейф на порядки больше. Отсюда и берётся `GradScaler`.

## Что такое тензор

Многомерный массив чисел. По сути `numpy.ndarray` плюс три вещи:

- **`device`** — лежит на CPU или на GPU;
- **автоград** — `requires_grad`, `grad_fn`, `.grad`;
- поддержка GPU-операций.

Ключевые атрибуты: `shape`, `dtype` (обычно `float32`), `device`.

Скаляр — тензор формы `()`, вектор — `(n,)`, матрица — `(n, m)`.
«Тензор» не означает «многомерный».

Батч изображений в PyTorch — **`(N, C, H, W)`**: количество, каналы, высота, ширина.
В TensorFlow порядок другой — NHWC.

`model.to(device)` переносит параметры и буферы **на месте** и возвращает себя;
`tensor.to(device)` возвращает **копию**, её надо присвоить.

# Микро-эксперименты (пройдены)

1. Повторить бумажный расчёт в PyTorch: `w`, `c` как тензоры с `requires_grad=True`,
   forward, `backward()`, сверить `w.grad` и `c.grad` с ручной функцией.
2. Посмотреть `grad_fn` и `is_leaf` у промежуточных `a`, `b`, `L` (не у `w`!).
   Что в `.grad` у `b` после backward и почему.
3. Вызвать `backward()` дважды без нового forward — прочитать текст ошибки.
4. Цикл из 5 итераций без `zero_grad` и без `step` — увидеть 12, 24, 36, 48, 60.
   Потом добавить обнуление.
5. Одно и то же выражение внутри и снаружи `torch.no_grad()` — сравнить
   **у результатов** значение, `requires_grad` и `grad_fn`.
6. 10 шагов спуска при `lr = 0.05 / 0.2 / 0.3` с печатью `L` — проверить
   `q = 1 − 2·lr·(x²+1)`.
7. `b.retain_grad()` перед `backward()` — градиент появится (для `x=2, y=10, w=3`:
   `∂L/∂b = 2b = 6`).
8. `is_leaf` у тензора без `requires_grad` — `True`.

**Методический вывод из экспериментов 2 и 5:** прежде чем печатать, сформулируй,
что именно должно измениться. «Посмотрю, что там вообще есть» почти всегда даёт
пустой результат — трижды подряд измерялся не тот объект.

# Проверочные вопросы и ответы

**1. Что делает `loss.backward()` и что не делает?**
Считает градиенты цепным правилом и **прибавляет** их в `.grad` листьев.
Не обновляет веса — это `optimizer.step()`. Возвращает `None`.

**2. Почему `b.grad` пустой, связано ли это с освобождением графа?**
`.grad` заполняется только у листьев; `b` порождён операцией. С освобождением графа
не связано — оно удаляет сохранённые промежуточные **значения** и отвечает за ошибку
при повторном `backward()`. `.grad` живёт до `zero_grad()`.

**3. Условия заполнения `.grad`.**
Тензор — лист **и** `requires_grad=True`. Плюс практическое третье: участвует
в прямом проходе.

**4. Почему обратный проход дешевле?**
Один обратный проход даёт производные одного выхода по всем входам сразу
(≈2 стоимости прямого). Прямой режим потребовал бы прохода на каждый параметр.
Прямой выгоден при малом числе входов и большом числе выходов.

**5. Три способа выключить градиент.**
См. таблицу выше. Путают `no_grad()` и `eval()`; заменять друг другом нельзя,
на валидации нужны оба.

**6. `eval()` есть, `no_grad()` забыт — что пострадает?**
Скорость и память — да (граф строится, активации хранятся).
Метрика — **нет**: `no_grad` не влияет на арифметику, а `eval()` на месте.

**7. Лосс стоит на плато с первой эпохи.**
Гипотеза №1 — слишком большой LR (граница устойчивости). Параметры при этом
меняются сильно, колеблясь вокруг минимума.

**8. `total += loss`, где `loss` — тензор.**
Каждое слагаемое тянет живой граф своей итерации → утечка памяти и OOM.
Правильно `total += loss.item()` или `loss.detach()`.

**9. Забыт `zero_grad()`.**
`.grad` накапливается, реальный шаг растёт линейно с номером итерации
(12, 24, 36...). Специально накопление делают для большого эффективного батча
на маленькой GPU; обязательная деталь — делить лосс на число шагов накопления.

**10. Счёт (`x=3, y=2, w=1, c=2`).**
`a = 5`, `b = 3`, `L = 9`; `∂L/∂w = 18`, `∂L/∂c = 6`.
Точное попадание в минимум при `lr = 0.05` (`q = 1 − 20·lr = 0`).
Расходимость при `lr > 0.1` (`2/λ`, где `λ = 2(x²+1) = 20`); при `lr = 0.1` —
вечные колебания.
